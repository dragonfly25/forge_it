# 0014 — `forge init`, adapters, subagent rendering, `forge setup`, `forge profile`, radar

- Status: accepted
- Date: 2026-11-03

## Context

Phase 8 delivers the project templates, the ten prompts, the adapters that turn them into tool-native files, machine-level subagent rendering, `forge init`, `forge adapters generate`, `forge setup` and `forge profile`. Spec §12–§14 says to check the current Claude Code and Codex formats at build time. §14's radar workflow needs CLI support that no command provides yet. Kickoff items B9 (tool mapping) and B10 (radar comments) are settled here.

## Formats verified (2026-11-03)

**Claude Code** (https://code.claude.com/docs/en/skills.md, /memory.md, /sub-agents.md):
- `.claude/commands/<name>.md` still works, but commands have been merged into **skills**, and the docs say "Prefer a skill for new work".
- **Skill files**: `.claude/skills/<name>/SKILL.md`, with frontmatter `name`, `description`, `argument-hint` and others. Unknown fields are ignored.
- **Arguments**: `$ARGUMENTS` holds the full argument string. A skill wins over a command with the same name.
- **Imports**: `CLAUDE.md` imports another file with `@path` on its own line, resolved relative to the importing file, up to four hops.
- **AGENTS.md**: Claude Code reads it natively, but only when no `CLAUDE.md` exists, so an `@AGENTS.md` import stays the reliable path.
- **Subagents**: `.claude/agents/<name>.md` with `name`, `description`, `tools`, `model` (`haiku|sonnet|opus|fable|inherit` or a full id) and `effort` (`low|medium|high|xhigh|max`). Project files win over user files. This matches ADR 0002.

**Codex** (https://learn.chatgpt.com/docs/…, the new home of developers.openai.com/codex):
- **AGENTS.md**: read natively, concatenated from the repository root down to the working directory, with a default limit of 32 KiB in total.
- **Custom prompts**: `~/.codex/prompts` is **deprecated** in favor of skills and is user-level only.
- **Skills**: project-level `.agents/skills/<name>/SKILL.md` (and in parent directories up to the repository root) or user-level `~/.agents/skills`. Required frontmatter is `name` and `description`. Skills are invoked explicitly with `$name` or `/skills`, or implicitly by their description.
- **Subagents**: one TOML file per agent in `.codex/agents/` (project) or `~/.codex/agents/`. Required fields are `name`, `description` and `developer_instructions`; optional ones include `model` and `model_reasoning_effort`.
- **Effort**: `low|medium|high|xhigh` are safe values; the page also lists `max` and `ultra`, depending on the model.

## Decision

### Template tree (`src/forge/templates/project/`, loaded with `importlib.resources`)
`forge init` writes exactly these paths. The `forge init` snapshot test pins this list.

```
.forge/config.yml  .forge/team.yml  .forge/zones.yml  .forge/rules.md
.forge/prompts/{setup,plan,next,dev,sync,ship,review,status,handoff,release}.md
.forge/agents/{explorer,test-writer,reviewer}.md
specs/_template.md  plans/roadmap.yml
docs/decisions/_template.md  docs/forge/{onboarding,roles,faq}.md
.github/workflows/{forge-ci,forge-plan-apply,forge-radar}.yml
.github/ISSUE_TEMPLATE/forge-proposal.yml  .github/pull_request_template.md
.gitattributes  .gitignore  .env.example
```

Init then runs the project-level adapters, which add `AGENTS.md`, `CLAUDE.md`, `.claude/skills/forge-*/SKILL.md` and `.agents/skills/forge-*/SKILL.md`, depending on the adapters chosen. `docs/forge/commands.md` comes from `forge docs` in Phase 9.

### `forge init [--adapters generic,claude,codex] [--force]`
- **Defaults**: the adapters are `generic,claude,codex`, and `generic` is always included. The list is recorded in a new `adapters` key in `config.yml`, validated against the known adapter names.
- **Template placeholders**:
  - `{{project_name}}`: the repository directory name.
  - `{{repo}}`: `owner/name` from the `origin` remote when it is a GitHub URL, otherwise `<ORG>/<REPO>`.
  - `{{default_branch}}`: from `origin/HEAD`, else the current branch, else `main`.
  - `{{forge_version}}`: the version pin `>=X.Y,<X.(Y+1)`, from the CLI's base version.
  - `{{forge_install_ref}}`: the git ref the workflows install, `v<base version>`.
  - `{{github_login}}`: from `gh` when available, else `<github>`.
- **Existing files**:
  - A file that already exists is never overwritten without `--force`. Init lists the conflicts, writes nothing and exits 5 (precondition).
  - `.gitignore` and `.gitattributes` are merged instead: missing lines are appended, and nothing is removed.
  - `AGENTS.md` and `CLAUDE.md` follow the managed-region rule below.
- **Scope**: init never commits. It prints the next steps: edit `config.yml`, `team.yml` and `zones.yml`, then commit.

### Generated files and managed regions
- **Header**: every file an adapter writes starts with a "generated by `forge adapters generate` from <source>; do not edit" header, as a Markdown or YAML/TOML comment.
- **Managed region**: `AGENTS.md` and `CLAUDE.md` may hold human text. Forge owns only the region between `<!-- forge:adapter-begin -->` and `<!-- forge:adapter-end -->`.
  - Text outside the region is kept byte for byte.
  - A file without the region gets it appended at the end.

### Prompts (`.forge/prompts/<name>.md`, spec §12)
- **Frontmatter**: `name`, `description`, `args`, `roles`.
- **Required body sections**: Goal, Steps (the exact `forge … --json` calls), Exit codes (how to handle 0/1/2/3/4/5), Guardrails, Subagents (when to delegate and what to do without subagents), and Final report.
- **Test**: a test checks every shipped prompt for these sections, the frontmatter keys and that only real `forge` subcommands are named.
- **Subagent references**: prompts use the rendered names (`forge-explorer`, `forge-test-writer`, `forge-reviewer`) and always give a "without subagents, do it yourself" fallback.

### Adapters (`core/adapters/`, one module each, `render(project) -> list[GeneratedFile]`)
- **generic** (always): writes the managed region of `AGENTS.md`:
  - a project summary from `config.yml`;
  - the rules (`.forge/rules.md`), inlined;
  - the command table (name, description, args, roles);
  - the subagent list;
  - the instruction "when the user invokes `/<cmd>`, `/forge-<cmd>` or asks for it in words, read and follow `.forge/prompts/<cmd>.md`".

  It stays well under Codex's 32 KiB limit, because prompt bodies are referenced, not inlined.
- **claude**:
  - **Skills**: `.claude/skills/forge-<cmd>/SKILL.md`, with `name: forge-<cmd>`, `description`, `argument-hint` from `args`, and the prompt body with a closing `Arguments: $ARGUMENTS` line.
  - **`CLAUDE.md`**: its managed region holds `@AGENTS.md` and a short Claude note: commands are `/forge-<cmd>` and subagents are `forge-*`.
  - **Why skills**: skills, not `.claude/commands/`, because the docs prefer them.
  - **Why the `forge-` prefix**: Claude Code has built-in `/status` and `/review`, and teams keep their own names free. This **amends spec §13** (`.claude/commands/<name>.md`, `/next`) and §12's `/<cmd>` names. AGENTS.md maps `/<cmd>` and natural language to the same prompts, so both forms work.
- **codex**: `.agents/skills/forge-<cmd>/SKILL.md`, with `name` and `description`, and the prompt body. The body notes that arguments come from the user's message, because Codex skills have no argument placeholder. Custom prompts are deprecated, so none are generated. AGENTS.md is read natively.
- **`forge adapters generate [--check] [--local]`**:
  - **Plain**: rewrites the project-level files of the configured adapters. It removes generated `forge-*` skill directories whose prompt no longer exists, and only directories carrying the generated header.
  - **`--check`**: writes nothing. It exits 1 and lists every file that is missing, different or extra (used in CI).
  - **`--local`**: renders the machine-level files below from the current profile.

### Subagent rendering (machine-level, gitignored)
- **Source**: `.forge/agents/<name>.md` (§12.1). Its frontmatter is `name`, `description`, `tier` (`strong|standard|light|task`), `effort` and `tools` (`[read, edit, shell]`).
- **Which agent's models**: for each tool present in the profile's agents, Forge renders with one agent of that tool, the `default_agent` if it uses that tool, else the first one.
- **Model resolution**: the model comes from `models.resolve(agent, declared_tier=tier, roles=[name], constraints=config.models)`, so `min_tier_for` can raise it. `tier: task` renders as `inherit` for Claude and leaves `model` out for Codex, because the main session already runs the task's tier. An agent that cannot serve the tier is rendered with `inherit`/no model, and a warning is given.
- **Claude**: `.claude/agents/forge-<name>.md`, with `name: forge-<name>`, `description`, `tools`, `model`, `effort` (when the preset supports effort) and the instructions as the body. Tools follow the **B9** mapping: `read` → Read, Grep, Glob; `edit` → Edit, Write; `shell` → Bash.
- **Codex**: `.codex/agents/forge-<name>.toml`, with `name`, `description`, `developer_instructions`, `model` and `model_reasoning_effort` (only `low|medium|high|xhigh`). Codex has no per-agent tool list, so `tools` is not rendered.
- **Gitignore**:
  - **Patterns**: the template `.gitignore` adds `.forge/local/`, `.env.local`, `.claude/agents/forge-*.md` and `.codex/agents/forge-*.toml`.
  - **Check before writing**: `--local` refuses to write a rendered file that git would not ignore (`git check-ignore`). It exits 5 with a hint to add the pattern.
- **When files are re-rendered**: `forge setup`, `forge profile set` and `forge profile edit` re-render them (§6.5.3).

### `forge setup [--check] [--yes]`
- **Checks** (all of them in `--check`, and first in the interactive run). Each failed check carries a message and a fix:
  - git ≥ 2.38;
  - `gh` installed and ≥ `MIN_GH_VERSION`;
  - `gh` authenticated (`gh auth status`);
  - Python ≥ 3.11;
  - the CLI satisfying `forge_version` (when inside a Forge project);
  - a valid profile;
  - `check_profile` constraint violations;
  - preset drift (info);
  - rerere enabled in the repository;
  - machine-level adapter files up to date;
  - their gitignore patterns present;
  - clock skew against GitHub: the `Date` header of `gh api -i /meta`, warned above 5 minutes (Phase 3 known limit).
- **Exit codes**: `--check` exits 5 when a required prerequisite is missing. Warnings alone give 0.
- **Interactive flow** (plain `setup`). The core is a pure wizard driven by an injected IO protocol (ask/confirm/choose/print), so tests feed simulated input.
  1. Run the checks.
  2. Detect tools with an injected runner: `claude --version`, `codex --version`, `ollama list`.
  3. For each detected tool, propose an agent:
     - **Id**: `<tool>-<login>`, editable.
     - **Tiers**: the tool's preset tiers, with the project's `config.models.recommended` shown beside them. The user accepts or edits each tier and effort.
     - **Local models**: for `ollama`, the user picks a model per tier from `ollama list`, or none.
     - **Providers**: from the preset.
  4. Choose the default agent.
  5. Write the profile. It holds labels only, never credentials.
  6. Run `check_profile` and show violations as warnings.
  7. Enable rerere (`git config rerere.enabled true`, `rerere.autoupdate true`).
  8. Render the machine-level adapters.
  9. Run `config.setup.commands` from the repository root. Each one is shown and confirmed, or all are accepted with `--yes`.
- **`--yes`**: accepts every default without prompting.
- **Re-running**: with an existing profile, setup starts from it and only proposes changes.

### `forge profile show|set|edit`
- **`show`**: prints the profile and each agent's resolved tier → model and effort map.
- **`set <agent>.<tier|effort.level>=<value>`**: applies the change with the existing `apply_setting`, validates and saves.
- **`edit`**: opens `$VISUAL` (then `$EDITOR`, then `vi`) on a temporary copy, validates it, and replaces the profile only when the copy is valid. Otherwise it exits 1 and the old profile stays.
- **After a change**: the machine-level adapters are re-rendered when inside a Forge project.

### Radar (§14, B10): `forge refresh --radar`
- **What it does**: after the normal refresh, for each in-progress task:
  - **Zone drift**: count the commits on `origin/<default>` since the merge base with `origin/task/<n>` that touch the task's zones, merges excluded (the drift rule of ADR 0010).
  - **Stale lease**: check whether the lease is stale (ADR 0009).
- **Comment**: Forge keeps at most **one** comment per issue under `<!-- forge:radar -->`.
  - It lists the commits that touched the zones ("sync recommended") and/or the stale lease ("reclaimable with `forge reclaim <n>`").
  - It is updated only when its content changes, and deleted when there is nothing left to report.
- **Workflows**: `forge-radar.yml` runs it on every push to the default branch and hourly.

### Workflows (§14)
- **All three**:
  - install Forge pinned to `{{forge_install_ref}}` with `uv tool install`;
  - check out with `fetch-depth: 0`, because Forge refuses shallow clones;
  - use `GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}` with `permissions: {issues: write, pull-requests: write, contents: read}`.
- **Action versions**: `actions/checkout@v7` and `astral-sh/setup-uv@v10` (major tags; the latest releases on 2026-11-03 were v7.0.1 and v10.3.3).
- **`forge-ci.yml`** (pull requests): runs `forge adapters generate --check`, plus a clearly marked step where the project runs its own checks (the commands from `config.checks`, which the lead copies in).
- **`forge-plan-apply.yml`** (push to the default branch touching `plans/*.yml`): runs `forge plan validate` then `forge plan apply` for each changed milestone plan.
- **`forge-radar.yml`**: push to the default branch and an hourly schedule, running `forge refresh --radar`.

## Implementation notes (Phase 8)

**Init and adapters**
- **Header placement**: in `SKILL.md` and Claude subagent files, the generated header comes right after the frontmatter, because the frontmatter must be on line 1.
- **`adapters:` line**: init rewrites the single-line `adapters:` line of the template `config.yml`, so the template keeps that form.
- **Subagents follow the profile**: they are rendered for every tool in the profile, whatever `config.adapters` says.
- **`AGENTS.md` summary**: it has no `github.repo`, so editing the repository name does not make it stale.
- **`--check --local`**: reports machine-level drift and exits 1.
- **`write_local`**: returns only the files it changed.
- **Prompt check**: it accepts `release` and `docs` as planned commands until Phase 9 registers them. A reminder test fails once they exist.

**Setup and profile**
- **Severity**:
  - Errors, which make `--check` exit 5: a missing or invalid profile, a missing gitignore pattern, an invalid config.
  - Warnings: a version-pin mismatch, rerere off, outdated machine-level files, clock skew.
  - Info: preset drift, and a clock skew that could not be measured.
- **Failures in the interactive run**: with a missing prerequisite, setup still writes the profile and then exits 5. A failing setup command stops setup with exit 1.
- **Undetected tools**: re-running setup keeps profile agents whose tool is not detected.
- **Ollama with `--yes`**: no `strong` model; the first listed model for `standard` and `light`.
- **Clock skew via the protocol**: the check uses `GitHubClient.server_time()`, the `Date` header of `/meta`, so all GitHub access stays behind the protocol.

- **Subagents in task worktrees**: `forge next` renders the machine-level subagent files into each task worktree it creates or reuses, when a valid profile exists. A failure there is only a warning. `forge setup`, `profile set` and `profile edit` re-render into the main worktree and every task worktree.
- **Task worktrees and `--local`**: `forge adapters generate --local` renders only the current checkout. Task worktrees pick up the new files from `forge setup`, `profile set`/`edit` or their next `forge next`.
- **GitHub Enterprise**: the clock-skew check asks `gh`'s default host, which may not be the project's host there.
- **Non-Claude models**: a model that is neither a Claude alias nor a `claude-…` id renders as `model: inherit`, with a warning. This happens with hybrid agents such as `light: llama-local`.
- **Login check**: `setup --check` warns when the profile's `github` differs from the `gh` login.
- **Editor order**: `profile edit` opens `$VISUAL`, then `$EDITOR`, then `vi`, the usual convention.
- **Disabled adapter**: when an adapter is disabled, `--check` reports its leftover files as extra, including the `CLAUDE.md` region. A plain `generate` removes them.

**Radar**
- **No mentions**: logins, commit subjects and authors appear in code spans, so the comment never notifies anyone.
- **Scope**: only open task issues are scanned, so a radar comment on a closed issue is left alone.
- **Duplicates**: when an issue has several radar comments, the oldest is kept and the others are deleted.
- **Missing `zones.yml`**: the radar warns and writes nothing.

**Workflows**
- **Action versions**: `actions/setup-node@v7` appears in the commented example step.

## Consequences

- **Command names**: users type `/forge-next`, and so on, in Claude Code; Codex skills are `$forge-next`. Natural-language requests work everywhere through `AGENTS.md`.
- **Codex project config**: Codex's `.codex/config.toml` is not generated. Model choice stays in the machine profile and the rendered subagents.
- **Format drift**: when Claude Code or Codex formats change, only the adapter modules and this ADR change. Prompts stay provider-neutral.
